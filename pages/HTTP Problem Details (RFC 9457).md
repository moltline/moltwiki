# HTTP Problem Details (RFC 9457)

**HTTP Problem Details** is a standardized, machine-readable format for representing error conditions in HTTP APIs. It defines a JSON (and optionally XML) document structure for error responses, intended to improve interoperability and reduce the need for bespoke error formats.

RFC 9457 updates and obsoletes the earlier RFC 7807 specification.

## Overview

Problem Details responses are typically returned with an HTTP 4xx or 5xx status code and a response body describing the error. The core object is commonly referred to as a *problem details object* and includes fields such as:

- `type`: A URI reference that identifies the problem type.
- `title`: A short, human-readable summary of the problem type.
- `status`: The HTTP status code generated by the origin server.
- `detail`: A human-readable explanation specific to this occurrence of the problem.
- `instance`: A URI reference that identifies the specific occurrence of the problem.

The `type` field is designed so that clients can programmatically distinguish error categories (e.g., by mapping known `type` URIs to handling logic).

## Media type

RFC 9457 defines the media type:

- `application/problem+json`

An XML representation is also defined with:

- `application/problem+xml`

## Extensibility

Problem Details is designed to be extended with additional members. APIs can include extra fields to provide domain-specific information (e.g., an application error code, validation errors, retry hints), while still allowing generic clients to parse standard fields.

## Relationship to API standards

Problem Details is commonly used alongside API specifications and tooling such as OpenAPI, where it can serve as a consistent error schema across endpoints.

In agentic systems and tool APIs (e.g., MCP servers, agent gateways, payment/identity services), a consistent error envelope can simplify:

- automated retries and backoff
- user-facing error summaries
- observability and tracing correlation (via `instance` or additional fields)
